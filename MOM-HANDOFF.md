### Structure correction — current work

Explicit user direction, forwarded by `mom-and-graphs` on 2026-09-28: “These threads are ALWAYS hierarchical and have one or more centroids. They are NOT immutable because another one may pop up!”

Revise the data model before building further on the flat shape. Add a parent/child thread spine, a centroid role or pointer, and spawn/merge/fold lifecycle. Folding contracts a resolved thread's subtree into its parent's outcome, carrying unfinished obligations, governing constraints, and return points forward. The former five-peer demo failed to show origin, spread, or main-line-versus-tangent orientation.

The earlier sentence “relationships need not form a strict hierarchy” applied to cross-links and the whole forest—not to the threads themselves. It must not be used to justify a flat map. The implementation descriptions below describe the superseded flat baseline until the correction is checked.

Implementation plan under independent Astra review:

1. Represent a thread's centroid as the thread node itself, rather than duplicate thread and center objects. Every node has an explicit parent; only threads can be parents or roots. Parent links form a forest, independently of cross-links.
2. Spawn through a sourced thread insertion. Merge centers without flattening their surviving children. Fold a resolved thread's subtree into its immediate parent, keeping unfinished branches and standing constraints visible at the surviving center.
3. Return the main line, roots, focus path, and ancestor context with selected map reads. Keep the original request accessible alongside the current interpretation. Do not invent a numerical distance or radial placement.
4. Publish a new checkpoint format; preserve v1/v2 source history and cursors. Old flat maps remain labeled as old maps until Mom reconstructs the hierarchy from recorded evidence. Keep the old state on failure, and retain access to older folded history.
5. Check parent-cycle rejection, subtree contraction, carried obligations and constraints, center merges, orientation at depth zero, migration, and cold reopen. Then perform one bounded live check. No further replay-tuning programme, layout work, or process-health implementation.

### Model and ownership

- Store stable identities and labeled connections, plus explicit hierarchical thread membership, dynamic centroids, and pointers to the main line and focus.
- Use nodes for work, decisions, and findings. Work can be an entire exploration branch, not one message or tool call.
- Keep intended action distinct from observed progress. A proposal is not an obligation; a returned report is not proof or evidence of incorporation.
- Connections express relationships such as `returns_to`, `informs`, `governs`, and `depends_on`. They can cross branches and form cycles; the model is not restricted to a tree.
- Keep source references on the interpretations they support. The recorded session remains the source history.

### Updates and active compaction

Mom submits one atomic batch against the current graph revision. The wire contract uses `removeEdges`, `upsertNodes`, `upsertEdges`, `folds`, and `removeNodes`, applied in that order; unused groups are empty arrays. Pi's strict transport rejects object unions, and Codex rejects `uniqueItems`, so the schema uses grouped edits and local uniqueness checks. Unchanged nodes and connections remain untouched. An explicit question can finish with an answer and no graph edits; it does not require a complete map rewrite.

A fold names the exploration being compacted, its surviving outcome, and the treatment of connections to the rest of the graph. Mom carries unfinished work, governing constraints, and return points forward. The host rejects dangling connections or deletion of the current purpose/focus without an explicit replacement. Omission from an edit batch never means deletion.

Folding removes detailed exploration from the maintained active graph, not merely from the display. A checkpoint reference identifies the prior interpretation; original source references identify the evidence. Opening that history is a read-only view, not restoration of obsolete work into the active graph. Obsolete interpretations can be removed explicitly; there is no requirement to preserve every cited claim forever.

Code checks identities, connection endpoints, source references, revision conflicts, and atomic persistence. It cannot certify that Mom has retained every meaningful obligation or interpreted user permission correctly. Those remain semantic responsibilities, checked against the actual conversation during the live demonstration.
